# PJ1 Phase 1：CLI SVG 编辑器

本项目使用 TypeScript 和面向对象方式实现命令行 SVG 编辑器。用户输入命令后，程序修改内存中的图形树，再保存为浏览器可以打开的 SVG 文件。本阶段支持矩形、圆、椭圆、线段、文字和普通分组六种类型。

## 一、架构方案

### 1. 模块划分

项目按“接收输入、执行操作、维护图形、读写文件”划分职责。

| 模块或目录 | 职责 |
| --- | --- |
| `src/cli/`：命令行交互 | 接收逐行输入，处理引号和注释，找到对应命令，统一打印错误和结果。 |
| `src/application/`：应用流程 | 管理当前文档、保存路径、撤销重做，提供图形工厂和存储接口。 |
| `src/application/commands/`：具体命令 | 每个命令类负责一种操作，调用图形和文档的方法。此目录属于 application 模块。 |
| `src/domain/`：图形模型 | 保存图形数据，实现几何操作、属性校验、树结构和 ID 唯一性等规则。 |
| `src/infrastructure/`：文件与 SVG | 将图形树与 SVG XML 文本互相转换，完成文件读取和保存。 |
| `src/main.ts`：程序入口 | 创建需要的对象，把具体存储工具交给应用会话，再启动命令行。 |

此外，`test/` 存放自动化测试，`scripts/` 存放架构检查脚本，`examples/` 存放示例命令和 SVG 文件。

### 2. 设计模式的选择

**Command（命令模式）**

选择原因：创建、删除、移动等操作需要统一执行，而且一条编辑命令应对应一个撤销单元。

实现方式：所有命令继承 Command，通过 `execute(session)` 执行。可撤销的编辑命令进一步继承 EditCommand，通过 `apply(document)` 完成具体修改。MoveCommand 负责移动，SetCommand 负责修改属性，其他操作各有对应类。

EditCommand 将编辑过程交给 EditorSession 统一管理，避免各个命令重复维护历史。具体命令通过 `undoMessage(...)` 描述恢复结果，确保撤销后的坐标、文字和父容器反馈正确。

**Composite（组合模式）**

选择原因：同一个移动或缩放命令既要处理单个图形，也要处理包含多层子图形的分组。

实现方式：五种叶子图形与 Group 都继承 Shape，具有统一操作方法。叶子维护自己的几何属性；Group 保存子图形，并将移动、缩放递归传递给孩子。例如，移动包含矩形和文字的分组时，两者会一起移动，命令不必分别判断类型。

删除由 SvgDocument 移除目标节点，目标是分组时会一起移除整棵子树。分组的公共样式写在 g 元素上，通过 SVG 样式继承生效。

**Memento（备忘录模式，使用文档快照）**

选择原因：删除、分组、跨容器移动可能同时影响多个节点，逐项编写反向操作容易遗漏结构或顺序。

实现方式：HistoryEntry 保存命令对象、修改前后的文档深拷贝和成功反馈。undo 恢复修改前的文档，redo 恢复修改后的文档。EditorSession 用两个栈管理撤销与重做；撤销后发生新编辑时清空重做栈。

Command 负责组织操作，Memento 负责恢复状态。


### 3. 依赖方向规则

| 模块 | 允许依赖 | 原因 |
| --- | --- | --- |
| domain | 本模块 | 图形规则独立于终端、文件系统和交互方式。 |
| application | 本模块、domain | 组织图形操作，通过本层定义的存储接口请求读写。 |
| cli | 本模块、application、domain | 解析输入并调用应用功能，允许使用领域类型，不直接处理文件存储。 |
| infrastructure | 本模块、application、domain | 实现应用的存储接口，并转换领域对象。 |
| main.ts | 上述模块 | 作为入口创建对象并连接依赖。 |

domain 和 application 不直接使用 Node 文件 API，也不导入 cli 或具体的 FileDocumentStore。这样更换输入方式或文件实现时，图形规则无需跟着改变。违反上述规则的依赖应列为待处理项。

按名字分派集中在两处：CommandRegistry 将命令名对应到命令类，ShapeFactory 将类型名对应到图形类。这两处注册表均列为后续插件化阶段的待重构项。

### 4. 变化点假设

-  **交互方式可能从命令行扩展到图形界面：** 
  如果以后通过按钮或鼠标编辑图形，移动、分组和撤销等规则仍然需要使用。因此，当前把终端输入解析与应用流程、图形模型分开，让新的界面可以复用已有操作。

- **可能增加 box 等新的图形类型：** 
  创建不同图形的规则集中在 ShapeFactory 中，移动、缩放等通用操作通过 Shape 提供的统一方法执行。这样增加类型时，主要扩展图形类和工厂中的注册项，不必在每个编辑命令中重复判断类型。

- **可能增加新的编辑命令：** 
  目前每种操作都有独立的命令类，命令名与实现的对应关系集中在 CommandRegistry。增加操作时，可以新增命令类并登记到注册表中，已有命令的实现通常不需要修改。

- **文档的存储方式可能变化：** 
  当前将 SVG 保存在本地文件中，以后可能需要保存到其他位置。为此，EditorSession 通过 DocumentStore 接口请求读写，具体文件处理由 FileDocumentStore 完成，更换存储工具时可以保留大部分应用逻辑。

- **文档规模和编辑历史可能增大：** 
  当前每次编辑都保存完整的前后快照，便于准确恢复分组、删除等复杂操作。但图形和历史记录越多，内存占用也会越大。本阶段优先保证功能正确，暂未设置历史条数上限。以后遇到较大文档时，可以考虑限制历史数量，或只记录发生变化的部分。

## 二、过程记录

本次协作中，我对照要求文档核对了 AI 生成程序的实际输出，发现撤销和重做的反馈存在问题：

1. **对照题目示例，发现输出与操作结果不一致。** 我将实际命令输出与要求文档中的典型会话进行比较，发现移动圆形后执行 undo，程序仍显示移动后的坐标 `(130,100)`，而示例应显示恢复后的 `(100,100)`。修改标题后撤销，反馈仍是新标题 `"My Diagram v2"`。删除矩形后撤销，反馈里仍然出现 `deleted`，没有说明图形已经恢复。这些输出容易让人误以为撤销没有生效，因此我把实际输出和题目示例一起发给 AI，指出两者不同。

2. **检查代码，确认问题出在反馈生成方式。** AI 根据我提供的会话检查了 MoveCommand、SetCommand、DeleteCommand 和 HistoryEntry。检查发现，撤销时文档快照已经恢复，但 HistoryEntry 只是给原来的成功消息加上 `undone` 前缀，没有根据恢复后的状态重新生成反馈。redo 也只是给原消息加上 `redone` 前缀。

3. **根据反馈含义修正实现。** 针对这些差异，AI 修改了各编辑命令的撤销反馈：撤销移动时显示原坐标，撤销属性修改时显示旧值，撤销删除时显示图形恢复到的父容器。例如 `circle#c1 moved back to (100,100)`。

4. **补充测试，验证输出和数据状态。** 原有测试主要检查撤销后文档是否恢复，没有逐行核对用户看到的反馈，所以没有及时发现这一问题。AI 随后把我提供的典型会话加入回归测试，逐行比较移动、undo、redo、文字恢复和删除恢复的输出，同时检查对应的坐标、文字内容和父容器是否正确。修正后，17 组测试和架构检查均通过。


## 三、一致性自查

### 1. 实际模块划分是否与方案一致

实际业务目录与方案一致，分别为 cli、application、domain 和 infrastructure。具体命令集中在 application/commands，文件读写集中在 infrastructure，domain不处理输入输出，没有发现模块划分偏差。

### 2. 是否违反依赖方向规则

抽样检查一些代码，没有违反依赖方向规则：

| 检查对象 | 实际依赖与判断 |
| --- | --- |
| domain/Shape.ts | 只依赖领域内的 Value，不使用终端或文件 API。 |
| application/commands/MoveCommand.ts | 使用应用层命令基类、参数校验和领域层 SvgDocument，符合 application → domain。 |
| application/EditorSession.ts | 依赖 DocumentStore 接口，未直接导入 FileDocumentStore。 |
| infrastructure/FileDocumentStore.ts | 使用 DocumentStore、SvgDocument、SvgCodec 和 Node 文件 API，符合基础设施模块职责。 |
| cli/CommandProcessor.ts | 调用应用会话和 CLI 解析器，不直接读写 SVG 文件。 |


## 四、质量保证手段

**功能完整性**的判断以要求文档中的命令、操作规则和示例会话为依据。**代码质量**的依据主要来自自动化测试、实际命令回放、严格编译和模块依赖检查。

### 1. 对照要求，检查功能是否有遗漏

首先按使用过程核对功能：能否新建画布、读取已有文件、修改尺寸并保存；能否创建六种内置图形，将它们放入指定分组，再进行移动、缩放和属性修改。每种图形都有对应测试，检查修改后的具体坐标和尺寸，确认操作结果符合题目规定。

对于分组相关功能，测试进一步检查 group、ungroup、addto 和 delete 执行后的父子关系及节点顺序。例如，解散嵌套分组后，子图形是否在原位置提升到父级；删除分组后，其内部图形是否一起消失。front/back 也会检查同级节点顺序，确认不会影响其他容器中的图形。

tree、show 和 help 的核对重点是信息是否足够使用：结构树中要能看到关键几何属性，图形详情要说明父容器和属性，帮助信息要列出支持的命令。此外，输入处理还检查了双引号文本、带空格的文件路径、整行注释和 Windows 换行符。

### 2. 检查连续操作和错误情况

单条命令正确，还不能说明连续编辑时不会出错。因此，测试会组合执行创建、移动、分组、删除、undo 和 redo，并比较每一步的文档状态。重点检查一条编辑是否只需撤销一次、撤销后进行新编辑是否清空重做记录，以及 tree/show/help 等显示操作是否保留历史。

题目对文档类操作有特别规定，测试也检查成功的 init/read/save 和画布尺寸修改之后，undo/redo 是否被禁止，以及下一次成功编辑后能否重新使用。文件读写失败时，则检查原文档、保存路径和历史是否仍然保留。

错误情况包括重复 ID、目标不存在、父节点不是容器、修改不允许的属性、缩放倍数非正数和非法祖孙关系等。测试会在执行前后比较文档，确认程序报错后没有留下部分修改。递归缩放还故意让后面的子图形发生数值溢出，用来验证前面已经完成的修改也不会影响正式文档。

### 3. 验证实际命令流程和保存结果

项目提供了 `examples/flowchart.txt`，其中包含创建分组、放入矩形和文字、移动、撤销以及保存等操作。这份命令已实际回放，并生成 `examples/flowchart.svg`，其中包含 3 个分组、2 个矩形、2 个文字和 1 条线段。自动化测试也通过真实 CLI 子进程输入命令，检查程序遇到错误后能否继续处理下一行。

对于文件保存，测试会先将文档转成 SVG，再读回并比较内容，检查层级、顺序、几何属性、样式和文字是否保持一致。中文、emoji、引号、& 和 < 等内容都有对应的转义与还原检查。外部 SVG 缺少 ID 时，还会检查自动编号是否避开已有名称，并输出警告。

### 4. 自动化检查验证代码质量

在项目根目录执行以下命令，可以运行完整检查：

```powershell
npm run check
```

该命令依次完成 TypeScript 编译、自动化测试和架构检查。最近一次验证中，17 组测试全部通过。

这些检查分别提供不同方面的依据：严格编译帮助发现类型使用错误和未使用代码。自动化测试用明确的预期结果检查功能，修改代码后可以再次运行，确认没有破坏已有行为。架构脚本检查模块是否依赖了不该依赖的代码，以及是否遵守一类一文件、类名与文件名一致等约定。

对代码质量的信心来自上述检查的共同结果，尤其是复杂结构操作、失败不改状态和已发现问题的回归验证。测试通过并不意味着已经覆盖所有输入，因此还需要对实现范围和限制的说明。

### 5. 明确验证范围和实现限制

当前验证针对 Phase 1 的六种内置图形和 CLI 操作。SVG 读入支持这些元素及其几何、公共样式属性，尺寸支持数值或 px，viewBox 需与 `0 0 width height` 一致。外部 transform、style、font-size、text-anchor、path 和 tspan 等内容暂不支持，读入时会报错。带有 `data-kind="box"` 的 g 可以作为普通分组读入，但不具有 box 插件的专用行为。

对于题目未完全明确的细节，当前约定为：init 只给宽度时，高度默认 600；修改 canvas 尺寸需同时提供宽高；group 将新组放在画布根的最后，成员保留操作前的文档深度优先顺序。分组变换直接修改子图形的几何属性，缩放不改变 stroke-width。无参数 save 使用最近一次成功 read/save 的路径，init 清除该路径。

文件处理还采取了两项措施：保存时先写同目录临时文件，成功后再替换目标；读取时先构建临时文档，解析成功后再替换当前文档。这样可以减少读写失败对已有内容的影响。当前撤销采用完整快照，没有历史条数上限，因此尚不能据此判断超大文档下的性能表现。
